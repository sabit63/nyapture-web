# 連携API・お気に入り仕様

更新日: 2026-09-12
状態: 議論で確定した方針。機能実装・APIの具体的な契約定義は未着手。

## 1. 前提と構成

Webに検索・Book共有のAPIと、お気に入りを保存・同期するAPIを設ける。
通知基盤としてntfyサーバーを使用する。本書のサービス側とはWeb APIサーバー側の配信・保存処理を指す。
本書の議論・実装対象は、このリポジトリで実装するWeb APIサーバーの仕様とする。
接続クライアントについてはAPI契約に必要な動作・前提のみを記載し、ViewerのUI詳細や別リポジトリの実装手順は扱わない。

AND／OR検索、JSTでの日時表示、更新日ソートは対応済みとして連携を設計する。
これらの統一実装は別作業とする。状態条件・タグ欠落条件の対応差は残る。

Web API・ntfyへの接続はTailscaleの閉じたVPN内で行う。ViewerはWebのAPIエンドポイントを設定する。
Android端末ではntfyアプリをUnifiedPushの配信役（distributor）として使用し、ViewerはUnifiedPush connectorで通知を受け取る。
Viewerは取得したプッシュエンドポイントと暗号化用の公開鍵・認証シークレットをWebへ登録する。
Webは登録情報の更新・解除を扱い、通知は対応するWeb Pushライブラリで暗号化して送信する。
登録先URLは設定済みのntfyサーバーに限定する。端末同士のペアリングは行わない。
Web APIに独自ログインを設けずTailscale側でアクセスを制限する方針とする。ntfy側にはUnifiedPush用の送受信権限を設定する。
エンドポイントの案内による設定の省力化を想定するが、QRコードなどの具体方式は未確定。
プッシュは「共有あり」「お気に入り更新あり」という更新通知とし、共有内容・お気に入り本体はWebのHTTP APIから取得する。
Web APIサーバーはViewerとの通知用常時接続を管理せず、ntfyサーバーと端末のntfyアプリが通知経路を担う。
API契約はViewerの実装言語に依存させない。FlutterのAndroid版でも公式のunifiedpushパッケージで同じ構成を利用できる。

## 2. 検索・Bookの共有

| 共有種別 | 内容 |
| --- | --- |
| Book | 実際のBook識別情報を送る。Book本体は既存のコンテンツ取得経路から取得する |
| 検索条件 | 条件を送り、受信側で再検索する。送信時と結果が変わる場合がある |
| 検索結果 | 送信時の検索結果全件のBook一覧と並び順を送る。表示中のページだけに限定しない |

検索条件と検索結果は送信時に選択できる。
受信側が未対応の条件を含む検索条件は送信不可とし、その旨を表示する。
状態条件・タグ欠落条件を黙って省略しない。
Bookの識別情報に画面表示用の代替IDを使用しない。

共有は登録済みの全Viewerを対象とし、Webは各端末のプッシュエンドポイントへ更新通知を送る。個別・複数端末を選択するUIは設けない。
複数Viewerの接続に対応する。

## 3. 配信・再配信キャッシュ

| 項目 | 確定仕様 |
| --- | --- |
| 保存方式 | Web側のメモリ内キャッシュ。再起動で失われてよい |
| TTL | Webが送信を受け付けた時点から10分。再送しても延長しない |
| 上限 | 検索条件・検索結果・Book共有を合算して100件 |
| カウント | 送信要求1回を1件とする。検索結果内のBook数では数えない |
| 上限超過 | 古い送信情報から破棄する。未受信端末があっても保持上限を優先する |
| 期限切れ | キャッシュから削除し、以後は配信しない |

キャッシュは共有内容を遅延配信するために保持する。
Viewerは通知受信時・新規登録時・再接続時に、Web APIからキャッシュに残るTTL内の未受領分を取得する。
新規登録端末には、登録前に受け付けた共有内容も配信する。
取得APIはWebが送信を受け付けた順（古い順）に共有を返し、その端末が受領済みの共有は対象から除く。通知の到着順には依存しない。
Viewerが受信内容を端末に保存し、Webへ受領応答した時点で、その端末への配信を完了とする。
ntfyへの送信成功やUnifiedPush内の応答を、Webへの保存後の受領応答の代わりにはしない。
ユーザーが内容を開くことは配信完了の条件にしない。
クライアント側の前提として、共有内容はViewerの受信箱に保存し、利用者が選んで開く。
Web APIサーバーは端末への配信と受領応答を扱い、受信箱のUIや開封状態の管理は対象外とする。
応答が失われて再配信されても、共有IDで重複保存を防ぐ。

TTL・件数上限は配信用キャッシュに適用する。お気に入りの永続保存・同期には適用しない。
この10分・100件はWeb側の共有キャッシュの制限とし、通知が遅れて届いても期限切れ・破棄済みの共有は取得APIから返さない。
複数端末への通知送信で共有キャッシュの件数は増やさない。ntfy側の通知キャッシュの具体設定は未確定とする。
受信済み端末内のデータをTTLで削除する仕様ではない。

## 4. Webのお気に入り

Webのお気に入りを永続保存する。Book・タグのお気に入りと、その整理用ラベルを対象とする。
Webのお気に入りの本体は、本リポジトリで実装するサーバー側の保存データとする。
Viewer内のWebのお気に入りは表示用の複製とし、サーバーと一時的にずれてもよい。
複数Viewerで同じWebのお気に入りを共有し、ラベルで整理できる。
Webのお気に入りはWebで編集可能とし、Viewerからもオンライン時に追加・編集・削除できる。
初期の「Webは参照のみ」という制限は採用しない。

ViewerはWebのお気に入りの表示に先立って、最初の同期でサーバーの最新状態を取得する。
接続中は変更通知を契機に自動同期し、再接続時にも最新状態を取得する。

### 4.1 競合とオンライン編集

お気に入り・ラベルの項目単位で、Webが後から受け付けた変更を採用する。
削除も変更として扱い、端末の時計は後勝ちの判定に使用しない。
Viewerの古い一覧でサーバーの一覧を全体置換せず、Viewerの一覧に存在しないことだけを理由にサーバー側の項目を削除しない。

ViewerからWebのお気に入り・ラベルを追加・編集・削除する操作はオンライン時のみとする。
オフライン変更の保持や、再接続時の未送信変更のアップロードは行わない。
サーバーの保存確認をもって変更完了とし、通信失敗時は変更完了として扱わない。
再送による二重登録を防ぐ。
以前の「競合を利用者に確認する」方針は、項目単位の後勝ちに置き換える。

### 4.2 ローカルのお気に入りとの分離

Viewerの既存ローカルお気に入りと、同期対象のWebのお気に入りは別に扱う。
Viewer自身のお気に入りの本体はローカル側とし、Webのお気に入りとは独立して保持する。
Webのお気に入りの自動同期で、ローカルお気に入りを変更・削除しない。
初回接続時に既存ローカルお気に入りを自動統合しない。

ローカルお気に入りをWebへアップロード可能にする。
Webのお気に入りをローカルへ取り込む操作は手動とする。
アップロード時の同一項目や同名ラベルの対応付けは、サーバー側の未確定事項とする。
コピーか移動か、対象選択の単位、ローカルへの取り込み時の重複処理はViewer側の仕様として本書の議論対象外とする。

## 5. 未確定事項

以下は実装前に決める。確定仕様として補完しない。

1. APIパス・データ形式、登録端末の識別と登録情報の更新・解除、Web API・ntfyの接続制限と権限の具体設定。
2. ntfyへの通知失敗時の再試行・失効エンドポイントの扱い、通知再送条件、ntfy側の通知キャッシュ設定、Web側の共有キャッシュのデータ量上限。
3. お気に入り・ラベルの識別、削除記録と再送の扱い、アップロード時の重複処理。
4. 複数のコンテンツ取得先を利用する場合のBook識別と接続先の対応付け。

## 6. 実装時の確認事項

1. 全登録Viewerのエンドポイントへntfy経由で更新通知を送り、共有本体はWeb APIから取得できる。保存後の受領応答と共有IDによって端末単位の重複を防げる。
2. 新規登録・再接続時はキャッシュ内のTTL内の未受領分を受付順（古い順）に配信し、新規登録端末には登録前の共有も届く。10分経過・101件目の追加・Web再起動で保持ルールが守られる。
3. 検索結果全件の順序が保持され、検索条件の未対応部分が黙って除去されない。
4. 初回同期・再接続時にWebのお気に入りの最新状態を取得できる。お気に入り・ラベルの変更は項目単位の受付順で反映され、保存完了後に成功応答と変更通知を返す。
5. 同期APIの対象はサーバーが保持するWebのお気に入りとし、Viewerのローカルお気に入りの変更・削除を要求しない。
